# Gradle Artifact Publishing to Sonatype Nexus Repository Manager

## Project Overview

This project demonstrates how to build a Java application using Gradle and publish its build artifact to a remotely hosted **Sonatype Nexus Repository Manager**.

The goal is to understand how artifact management works in a DevOps environment, particularly how developers can publish and store application artifacts in a centralized repository instead of relying only on local build directories.

The Nexus Repository Manager instance is hosted on a DigitalOcean Ubuntu Droplet, while Gradle is configured locally to communicate with Nexus and publish the Java artifact.

## What I Implemented

### 1. Provisioned a DigitalOcean Droplet

Created an Ubuntu Droplet to host Nexus Repository Manager.

The server provides the infrastructure required to run Nexus and make the repository accessible remotely.

### 2. Configured Cloud Firewall Rules

Configured inbound firewall rules to control access to the Droplet.

Important ports:

| Port | Purpose |
|---|---|
| 22 | SSH remote administration |
| 8081 | Nexus web interface and repository access |

**Troubleshooting experience:**

During the exercise, I encountered an SSH connection failure because my public IP address had changed.

The DigitalOcean inbound firewall rule still allowed SSH access only from my previous IP address.

After investigating the issue and receiving assistance from the support team at my training centre, I updated the firewall rule with my current IP address and successfully restored SSH access.

This demonstrated the importance of understanding source IP restrictions and cloud firewall configuration.

### 3. Installed Nexus Repository Manager

Installed Nexus Repository Manager 3.98.1-01 on the Ubuntu server.

Nexus provides a centralized location for storing and distributing software artifacts.

The installation uses the following directories:

- Installation: `/opt/nexus-3.98.1-01`
- Data directory: `/opt/sonatype-work/nexus3`

Nexus web interface:

```text
http://YOUR_DROPLET_IP:8081
```

### 4. Configured Maven Hosted Repositories

Created a Maven hosted repository named:

`maven-snapshots`

A hosted repository stores artifacts produced internally by a development team.

Snapshot versions are useful during development because they represent work that is still evolving.

The repository endpoint follows this format:

```text
http://YOUR_DROPLET_IP:8081/repository/maven-snapshots/
```

### 5. Configured Nexus Users, Roles and Permissions

Worked with Nexus security configuration to understand how users and roles control access to repositories.

The objective was to provide the developer account with the permissions required to publish artifacts to the Maven snapshots repository without granting unnecessary administrative privileges.

This introduced the practical importance of role-based access control (RBAC).

### 6. Configured Gradle Publishing

Configured the Gradle project to use the Maven Publish plugin.

The publishing configuration connects Gradle to the Nexus hosted repository.

The configuration includes:

- Maven publication definition.
- Artifact file and version.
- Nexus repository URL.
- Repository authentication credentials.

Example publishing configuration:

```groovy
apply plugin: "maven-publish"

publishing {
    publications {
        create("maven", MavenPublication) {
            artifact("build/libs/my-app-$version.jar") {
                extension "jar"
            }
        }
    }

    repositories {
        maven {
            name "nexus"
            url "http://YOUR_DROPLET_IP:8081/repository/maven-snapshots/"

            allowInsecureProtocol = true

            credentials {
                username project.repoUser
                password project.repoPassword
            }
        }
    }
}
```

**Note:** The artifact path must match the actual JAR generated by the Gradle build.

### 7. Secured Repository Credentials

Repository credentials are configured outside the project in the local Gradle user properties file:

```text
~/.gradle/gradle.properties
```

Example:

```properties
repoUser=YOUR_NEXUS_USERNAME
repoPassword=YOUR_NEXUS_PASSWORD
```

The project references these values through:

```groovy
project.repoUser
project.repoPassword
```

Credentials should never be committed to GitHub.

## Building and Publishing

From the project root directory, run the following commands.

**1. Build the application**

Windows:

```powershell
.\gradlew.bat clean build
```

Linux/macOS:

```bash
./gradlew clean build
```

**2. Publish the artifact to Nexus**

Windows:

```powershell
.\gradlew.bat publish
```

Linux/macOS:

```bash
./gradlew publish
```

After successful publication, the artifact should be available in the Nexus `maven-snapshots` repository.

## Troubleshooting and Lessons Learned

This project involved practical troubleshooting beyond simply configuring the tools.

### SSH Connection Failure

**Problem:** Unable to connect to the Droplet as root.

**Cause:** The public IP address had changed, but the inbound firewall rule still referenced the previous IP address.

**Resolution:** Updated the SSH inbound rule to allow access from the current public IP.

### Gradle 401 Unauthorized

**Problem:** Gradle received an HTTP `401 Unauthorized` response when communicating with Nexus.

**Investigation:** Reviewed repository authentication credentials and Nexus user permissions.

**Resolution:** Resolved the authentication configuration issue and successfully proceeded with Gradle publishing.

### Nexus Ehcache Persistence Lock

**Problem:** Nexus logs contained an Ehcache persistence directory lock exception.

**Investigation:** Checked the running Java process, port 8081, application response and Nexus REST API.

**Finding:** Nexus was still responding successfully with HTTP `200`, despite the exception appearing in its logs.

This highlighted the importance of correlating application logs with actual service health rather than assuming that every logged exception means the entire application is unavailable.
